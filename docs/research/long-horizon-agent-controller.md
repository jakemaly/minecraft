# Long-horizon agent controller: focused research

This review focuses on the harness’s concrete failure modes: repeated deaths, losing the current plan, unverified progress, and noisy context. It uses original papers and project sources. The papers support mechanisms, not a claim that any one recipe guarantees a successful Ender Dragon run.

## What has useful evidence

- **Minecraft needs an observe–act–verify loop.** Voyager executes a Mineflayer program, feeds the next iteration the resulting game state and execution errors, and asks a verifier whether the milestone was actually achieved. It adds a skill only after verification. In its ablation, removing self-verification reduced discovered items by 73%; the authors call verification their most important feedback component. The implementation retrieves the five most relevant skills and changes task after four unproductive code-generation rounds. However, its verifier sometimes misjudged success, and its experiments target open-ended exploration with 2023-era models, not the Ender Dragon. [Voyager paper](https://arxiv.org/html/2305.16291)
- **Reflection works best as a corrective instruction tied to feedback.** Reflexion translates environment feedback into a short verbal direction for the next attempt and stores it in episodic memory. In one HotpotQA ablation, self-reflection added an 8-point absolute improvement over including the recent trajectory alone. Its authors also say the approach depends on self-evaluation and has no formal guarantee, so a model’s explanation must not be treated as proof of what caused a death. [Reflexion paper](https://arxiv.org/html/2303.11366)
- **Learn reusable lessons from outcome evidence; retrieve only relevant examples.** ExpeL compares failed and successful attempts at the same task, extracts recurring lessons, revises those lessons as later evidence supports or contradicts them, and retrieves similar successful trajectories. Its ablations support combining insights with retrieval. Evaluations cover WebShop, ALFWorld, HotpotQA, and FEVER, not Minecraft. [ExpeL paper](https://arxiv.org/html/2308.10144v3)
- **Separate “what should we do?” from “can we do it here?”** SayCan scores high-level language-model choices against low-level skill affordances/value estimates, grounding a suggested action in the current robot state. The useful harness analogue is to let the model choose a milestone while deterministic game-state checks gate dangerous or infeasible actions. The paper demonstrates robotics tasks; it does not establish a Minecraft safety system. [SayCan paper](https://arxiv.org/abs/2204.01691)

## Design implications for this harness

1. **Keep run control outside the model.** The daemon should own the objective, run lifecycle, retry counters, and success state. Ask the model to select or refine the *next milestone* and produce a bounded Mineflayer action. After execution, observe the world, verify the milestone from game/server evidence, update state, then continue. This adopts Voyager’s useful loop while keeping the user’s fixed Dragon objective instead of its open-ended curriculum.
2. **Use one compact, structured run ledger as the prompt’s source of truth.** Keep the full event log for humans and debugging, but give the model a short current-state summary: objective and authoritative completion check; active milestone and prerequisites; last verified progress; location/dimension; health, food, armor and equipment; respawn/recovery point; current hazards; recent failed strategy and the evidence for it. Include only a few task-relevant lessons or successful skills, not the growing raw transcript. Voyager and ExpeL both use state-aware tasking and relevance retrieval; neither establishes a specific token limit, so the cap should be measured against the selected model.
3. **Make death reflection evidence-first and actionable.** Base a reflection on the server’s death message and nearby event/state records when available. Store: observed evidence, cause with confidence (or “unknown”), a prevention rule, and the next recovery action. Do not let an unverified model guess become a durable fact. Track corroboration and counterexamples so a recurring lesson gains weight and a contradicted one can be revised, following ExpeL’s evidence-updating idea. The first follow-up should state what is different in the plan, such as returning to the same gear-free route being blocked until the required equipment is present.
4. **Gate risky steps with deterministic preconditions.** Before a hazardous expedition or combat action, check current game state against simple rules such as minimum health/food, available armor and weapon, required supplies, and a usable respawn/recovery point. Reject or defer the action when a precondition fails; return the exact failed condition to the planner. These checks are design recommendations, not findings proven by SayCan for Minecraft.
5. **Detect stagnation and force a plan change.** Count attempts with no verified milestone progress. After a small fixed number, stop repeating the same program, identify the missing precondition or change the subgoal/route, and preserve the overall objective. Voyager’s four-round cutoff is an existence proof for bounded retries, not a universal optimal value. Keep timeout/model failure distinct from an in-game failure so infrastructure errors do not produce false death lessons.
6. **Promote only verified reusable actions.** A successful Mineflayer script becomes a reusable skill only after a game-state verifier confirms its promised result; retain its preconditions and evidence. Retrieve a few skills relevant to the active milestone. This matches Voyager’s verified skill-library pattern and limits both risky copy-paste and context growth.
7. **Keep observation proportional to the decision.** Send compact state on routine turns and fetch a fresh image when visual information is needed; do not replay old frames as memory. This matches the user’s request to stop attaching an image to every response. The cited papers support grounding decisions in current observations, but do not evaluate this exact image policy.

## How to tell whether the changes work

- Replay the run’s death records and label each cause from server evidence before assessing reflection quality. Measure repeated deaths from the same evidence pattern, whether the next plan changes, and whether recovery preserves the same non-Hardcore world and run.
- Measure milestone progress only with authoritative game evidence (for Dragon completion, the configured advancement criterion), not a model declaration or a successful script exit code.
- Track verified milestone progress per action/model call, repeated no-progress attempts, deaths by cause, resource readiness before hazardous trips, model input tokens, and image count. Check that the same failure pattern is not retried while its blocking precondition remains unchanged.
- Add boundary tests for the controller’s state transitions, death reflection input, deterministic hazard gate, milestone verifier, retry/replan threshold, and memory retrieval. Keep the live Minecraft smoke test for end-to-end behavior; simulated traces cannot establish game-world reliability.

## Sources and limits

These sources are original research papers. Voyager is the closest match because it uses Minecraft and Mineflayer, but its goal is exploration. Reflexion and ExpeL provide evidence for learning from attempts in other domains. SayCan motivates grounded action selection in robotics. Treat the combined controller above as an evidence-informed design proposal that still needs validation on this harness’s real run traces.

## Echo: transferable experiences and the RL-replay track

Echo (CVPR 2026) is a useful extension to the Voyager/Reflexion picture, but it solves a different part of the problem. It stores successful Minecraft task experiences as Contextual State Descriptors (CSDs), then retrieves examples by five explicit dimensions—structure, attributes, procedure, function, and interaction—and asks a frozen-at-inference MLLM to analogically adapt a plan. The plan is checked for logical consistency and feasibility, then executed and externally validated; successes enter long-term memory while failures are logged. The paper uses instruction tuning to improve CSD formatting, so “no parameter updates” describes runtime task transfer, not the full training setup. [CVPR paper](https://openaccess.thecvf.com/content/CVPR2026/html/Li_Experience_Transfer_for_Multimodal_LLM_Agents_in_Minecraft_Game_CVPR_2026_paper.html), [official implementation](https://github.com/CatworldLee/Echo)

The paper reports faster item/task unlocking than Voyager on its custom crafting, functional-equivalence, crafting-chain, and utility-block benchmarks; the continuous-learning chart reports 45% success at episode 30 for Echo versus 18% for Voyager. This does not establish that Echo is better at survival or beating the Ender Dragon: it does not evaluate the Dragon objective, and its own discussion says Echo is weaker at active exploration and starts more slowly. JARVIS-1 is stronger in much of the cold-start table, so Echo should not be summarized as uniformly superior. Treat the speedup and 30-episode values as benchmark-specific results, not expected gains for this harness. [CVPR paper](https://openaccess.thecvf.com/content/CVPR2026/html/Li_Experience_Transfer_for_Multimodal_LLM_Agents_in_Minecraft_Game_CVPR_2026_paper.html)

For this controller, adopt Echo’s *representation and transfer test*, not its whole stack: store compact verified skill/episode cards with their prerequisite state, process, expected effects, outcome evidence, and which parts are world-specific. On a later run, retrieve a few analogous cards, explicitly name which dimensions match and which differ, propose an adaptation, check its preconditions, then verify the outcome in the live world before promoting it. A wooden-to-stone tool recipe is a good procedural transfer; a remembered Nether route or a death location should be treated as world/seed-specific unless state evidence supports transfer.

Echo does not provide the missing death-reflection policy. Its paper says successful tasks are written to the transfer memory and failed tasks are logged; it does not describe a causal death-reflection process that turns a failure into an enforced prevention rule. Keep incident reflection as a separate layer: preserve server-observed death evidence and the attempted action, let the model propose a cause and policy change with uncertainty, and have the controller verify that the next attempt satisfies that policy. A reflection can then become a negative constraint or a candidate reusable episode, while only demonstrated successful adaptations become positive skills.

Keep RL/world replay as a separate experimental arm. Echo's CSDs can be derived as annotations over recorded trajectories, but its in-context retrieval is not reinforcement learning and its paper does not evaluate replay-based policy optimization. Preserve raw observation/action/outcome traces and a stable initial-state/checkpoint record for replay; link them to CSD summaries and incident labels rather than replacing them. The Dragon controller should initially use retrieved cases as decision support for the existing model, while the replay track independently evaluates whether those cases or trajectories improve a learned policy.

## Updated delivery plan: Dragon-first, replay as a separate arm

The attached “Assess Minecraft world replay for RL” conversation is context for a second research track, not an instruction to replace the live objective. It narrows that track to short risk decisions and a synthetic text environment rather than training on whole Dragon campaigns. Keep the production controller focused on completing the Ender Dragon task; make its trace format useful to the replay track without coupling run success to a training experiment.

### 1. Record decision evidence once, for both tracks

Extend the existing append-only run trace so a meaningful decision can be reconstructed: run/world/checkpoint IDs; compact observation available to the model; action/tool/program identity; relevant preconditions; result observation; damage, death, or progress events; and links to the world save or image when available. Keep three fields separate: observed outcome, cause evidence, and model-suggested causal explanation. If the server cannot identify the cause, store `unknown`; do not turn a guess into a fact. This is needed because the current bot event is only `death`, while earlier run review found repeated drowning and hostile-mob deaths. [Current event handler](../../bridge/src/bot.js)

This trace also feeds replay cases. Preserve decision-time observations separately from hidden simulator/world state so later risk labels cannot use information the live model never had. The RL discussion correctly identified this as necessary to avoid hindsight bias. The full world save is useful when exact replay is feasible; otherwise store the causal constraints for a varied synthetic scenario.

### 2. Make the run ledger the source for the agent and GUI

Have the daemon persist a compact ledger per run: fixed objective and verifier; milestone IDs/status/evidence; active milestone and prerequisites; last verified progress; current recovery state; known spawn and recovery supplies; repeated-failure signatures; and named checkpoint references. Model output may propose milestone or plan changes, but only world evidence changes completion facts.

Render that same ledger inside the existing Marimo control panel (`notebooks/01_agent_runtime.py`): overall objective, milestone checklist, active step, last confirmed change, current blocker/recovery action, recent death lesson, and checkpoint time. Keep raw events, full tool output, and screenshots available on expansion. This gives the human and model one progress story without displaying hidden reasoning or parsing a growing free-form memory file as the source of truth.

Treat checkpoints as two related things:

- A **logical checkpoint** is the durable ledger plus verified world facts, recorded at each completed milestone.
- A **world checkpoint** is a server save/export at a few major risk boundaries, such as leaving the prepared Overworld base or entering the End. A bed, gear cache, and safe return route are recovery aids; they are not a rollback of the changed world.

Reuse the existing pause/save and export mechanisms initially. Add automatic named world copies only if restore-from-save tests show the current persistence is insufficient, since frequent full copies can consume substantial disk space.

### 3. Put the live Dragon run through a checkable controller loop

Use one compact loop: observe → select milestone → check preconditions → act → verify → update ledger → recover or continue. Keep the top-level Dragon objective stable while allowing milestone order and tactics to adapt to seed and world state. A starting milestone outline is: establish a safe Overworld spawn and recovery kit; gather suitable equipment and supplies; obtain Nether resources; locate and prepare the stronghold/portal; enter the End ready to fight; verify the Dragon advancement.

For each planned action, ask for the intended milestone, the key preconditions, and evidence that would prove the expected result. Deterministic checks should block clearly unready hazardous actions (for example, a dangerous expedition with no recovery plan or combat while missing required gear). Use game evidence for completion, not a model assertion or script exit status.

After repeated no-progress attempts with the same action and relevant state, force a changed plan or prerequisite before retrying. Start with a small threshold and tune it by replaying failures. A model/API timeout is an infrastructure event; it must not count as a death, a failed game strategy, or automatic evidence to stop a healthy long-running world.

### 4. Make reflections produce a testable change

After a death or significant near miss, build an incident from recorded evidence and ask the model for a structured candidate: cause and confidence; evidence references; what was knowable before the action; failed assumption; prevention rule; recovery step; and how to verify the rule next time. Keep an `unknown` cause valid. The controller should not promote the lesson just because the model wrote it: the next action must satisfy the proposed rule, and the outcome should be recorded as supporting or contradicting evidence.

Keep this reflection layer separate from the RL reward. Death and milestone completion can be simulator-verifiable; “this was an avoidable risk given the observation” needs a predeclared rule or a separately labeled teacher judgment. Keep observed outcome, ex-ante risk, and causal attribution as distinct labels.

### 5. Add Echo-style transfer without adopting its entire research stack

Represent a verified experience as a small case/skill card with five optional fields inspired by Echo: structure (layout/relations), attributes (materials, gear, health, oxygen), procedure (dependencies and action order), function (what resources/tools afford), and interaction (action and observed feedback). Include preconditions, expected postconditions, evidence, and world-specific constraints. On a new milestone, retrieve a few similar cases, state which dimensions transfer and which differ, adapt the procedure, and verify it in-world before promoting it.

Echo reports gains on its own crafting, equivalence, crafting-chain, and utility-block tasks, including 45% versus Voyager’s 18% at episode 30 in its continuous-learning comparison. This supports testing experience transfer here; it is not evidence of better Dragon completion. Echo stores successful tasks in its long-term transfer memory and logs failures; it does not supply the causal death-reflection policy we need. The paper also reports weaker active exploration and a slower initial learning phase, and JARVIS-1 is stronger in much of the cold-start comparison. Start with tagged JSON/case cards and a small retrieval set; do not build a vector database or a new multimodal memory service until simpler retrieval is shown to miss useful analogies. [Echo paper](https://arxiv.org/abs/2604.05533), [official Echo implementation](https://github.com/CatworldLee/Echo)

### 6. Build the replay/RL arm after event capture is reliable

Use real deaths and near misses as seeds for focused scenarios, not as a requirement to recreate every full campaign. First build a small text simulator for a few high-value cases (drowning/exhaustion, unarmored combat, lava/bridge crossing). Define a compact action set and validate each scenario’s state transitions. Let the objective reward useful progress, penalize death, and separately score avoidable risk based only on the observation. GRPO is a candidate training method from the attached discussion, not a prerequisite; first compare the baseline model and stored-lesson prompting on the same held-out scenarios.

Keep the terms distinct: this proposed arm is RL in a simulator with a designed reward (some outcome components are verifiable; ex-ante “avoidable risk” may need a declared rule or teacher label). OEL is a different approach: it extracts transferable experience and distills it into the model without an environment reward during consolidation. Continual Harness adapts prompts, skills, memory, and agent structure from trajectories, with separate process-reward training experiments. Both are useful references for the data/refinement loop, but their reported environments are text games or Pokémon, not Dragon survival. [OEL](https://arxiv.org/abs/2603.16856) · [Continual Harness](https://arxiv.org/abs/2605.09998)

Only after the simulator can reliably reproduce intended cases should it train or update a policy. Evaluate on held-out layouts, health/gear configurations, and routes; report survival, task completion, idle behavior, and action count together. Then test for transfer in controlled live Minecraft runs. Keep learned weights or policy changes out of the production Dragon controller until they beat the baseline without reducing goal completion.

### Acceptance checks and order

1. **Evidence and ledger:** simulated death, near-miss, timeout, and milestone traces persist across pause/resume; unsupported causes remain unknown; verified goal completion still comes from server advancement evidence.
2. **GUI:** the run page shows the same active milestone and progress as the ledger and identifies the last evidence/checkpoint; raw details can be opened without making the default view noisy.
3. **Recovery and anti-repeat:** a non-Hardcore death keeps the same run/world alive; repeat drowning or unarmored-combat signatures trigger a changed recovery/preparation step; unrelated infrastructure failures do not create false lessons.
4. **Experience transfer:** a retrieved skill/case is used only when its preconditions match, and adapted actions are externally verified before saving as successful experience.
5. **RL replay:** held-out scenarios show improved survival without collapsed task completion or idle policies; live transfer is measured separately from simulator reward.

Implement in that order through vertical slices, starting with event evidence and the daemon-owned ledger/UI. The RL track can begin collecting compatible data at the same time, but its simulator and training should not delay the Dragon controller. Track Dragon milestone completion, repeated deaths by supported cause, recovery time/loss, no-progress attempts, and verified progress per model turn; track simulator safety and completion separately.
